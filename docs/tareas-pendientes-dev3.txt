TSK-DEV3-201 - POST /v1/payments CON IDEMPOTENCY-KEY
Estado: PENDIENTE; el modulo Payments aun no contiene el caso de uso de pagos.

Implementar:
- Autenticar la API Key y derivar tenant y ambiente de esa clave; no aceptar
  esos valores del cuerpo de la solicitud.
- Validar monto, moneda, metodo de pago, referencia del comercio y token de
  pago pm_... recibido desde Stripe Elements.
- Reclamar en Redis la clave idempotency:<tenant_id>:<key> de forma atomica,
  guardar el hash canonico del cuerpo y establecer el TTL de 24 horas.
- Si la misma clave esta PROCESSING, responder 409. Si la clave se reutiliza
  con otro hash, responder 422. Si ya termino y el hash coincide, devolver la
  misma respuesta HTTP y cuerpo sin crear otro pago ni repetir el cobro.
- Persistir payment pending, payment_status_history y pago.creado en
  domain_event_outbox dentro de una transaccion de base de datos.
- Invocar al proveedor mediante PaymentProviderPort fuera de la transaccion
  de base de datos; despues persistir approved/rejected, historial y evento
  correspondiente en una nueva transaccion.
- Actualizar tenant_plan_usage sin contabilizar dos veces los reintentos y
  rechazar el pago cuando se exceda el limite del plan.
- Guardar la respuesta idempotente por 24 horas y liberar/recuperar el estado
  PROCESSING de forma definida ante errores y timeouts del proveedor.
- No importar el SDK de Stripe desde el modulo Payments.

Pruebas requeridas:
- Repetir la misma solicitud y clave devuelve la misma respuesta y crea un
  solo pago.
- Solicitudes concurrentes con la misma clave producen un solo procesamiento;
  la solicitud que encuentra el procesamiento activo responde 409.
- Misma clave con cuerpo distinto responde 422.
- Pago aprobado/rechazado persiste historial y eventos outbox correctamente.
- Limite de plan, timeout y error del proveedor no dejan una clave bloqueada
  indefinidamente ni generan cobros duplicados.
